# Knowledge Adapter 候補のレビューと実装判断

## 1. レビューの結論

6候補は、Rhinestoneの `Catalog -> Provider -> Result -> Resource` を補完する共有知識として
適切である。いずれもProviderから独立した意味を持ち、誤った解釈が別Resourceの選択、再現性
の喪失、利用条件の見落としにつながる。一方で、すべてを一度に実装すると「共通化のための
共通化」になるため、最小の不変値・根拠・失敗条件から垂直スライスを作る。

このレビューは、単に便利そうかではなく、次の問いで評価した。

1. 複数Providerが同じ意味を必要とするか。
2. Provider Adapterへ重複実装したときの誤差が大きいか。
3. 一次資料から解決結果を説明できるか。
4. 誤った既定値を入れた場合の被害が大きいか。
5. Coreのデータ取得・変換・解析責務を侵食しないか。

## 2. 候補別の判断

| 候補 | 適切性 | 価値 | 判断 | 先に証明すべきこと |
| --- | --- | --- | --- | --- |
| Identity | 高 | 非常に高い | 採用（第一の意味領域） | 期間付きコードと曖昧性を保持できること |
| Spatial | 高 | 非常に高い | 採用（第一の意味領域） | CRS・軸順・範囲を数値から分離できること |
| Temporal | 高 | 高い | 採用 | 暦年・年度・調査年を同じ整数にしないこと |
| Schema | 高 | 高い | 採用 | MIME type、論理形式、profile、版を分離すること |
| Provenance | 非常に高い | 横断的に非常に高い | 基盤として先行採用 | 根拠と取得時刻を保持し、secretを漏らさないこと |
| Rights | 高 | 高いが法的判断は不可 | 採用（情報保持に限定） | 不明・競合を「利用可」に変換しないこと |

## 3. Provenanceを基盤に先行する理由

IdentityやTemporalの結果は、辞書・コード表・制度解釈の版が変われば変化し得る。Spatialの
CRS定義やSchemaのprofileも、Providerの公開仕様に依存する。したがって、意味Adapterを先に
実装しても、根拠を記録できなければ同じ結果を再現できない。

ただし、Provenanceを完全な監査システムとして実装する必要はない。最初に必要なのは、既存の
`Metadata` と `Provenance` を拡張し、入力表記、解決値、Provider responseの識別、knowledge
snapshot、取得時刻、adapter versionを紐付けることである。PROV-Oの完全なグラフ化は後続の
選択肢とする。

## 4. 価値を高める設計上の修正

初稿のように「正規化する」とだけ書くと、実装者は不明値を既定値で埋める可能性がある。
レビュー後は全候補に次の制約を追加した。

- raw expressionとresolved valueを別々に保存する。
- 一意性、適用期間、根拠、スナップショット版を出力できるようにする。
- 未知・曖昧・未対応・取得不能を別の失敗として表現する。
- Provider projectionが情報を失う場合は成功扱いにしない。
- Knowledge Adapterがデータ取得や変換を始めない。
- 変更しやすい業務辞書をコードへ埋め込まず、注入可能なsnapshotにする。

この変更により、Knowledge Adapterは「入力をきれいにする便利関数」ではなく、解決の根拠を
持つ決定可能性の境界になる。

## 5. 実装ゲート

各候補は、次の順で実装可否を判定する。

```text
一次資料
  -> 小さな immutable value object
  -> 正常・曖昧・未知のfixture
  -> Source Adapterへの一つの統合
  -> Metadata / Provenance保持テスト
  -> 公開ガイドとAPIの整合確認
```

次のいずれかが満たせない場合、候補は「保留」とし、推測で実装しない。

- 標準またはProvider一次資料がない。
- canonical valueとProvider valueの写像が一意でない。
- 根拠のsnapshotを識別できない。
- 失敗時に利用者が入力を修正できない。
- Coreまたは既存Execution Adapterの責務を奪わないと実装できない。

## 6. 初期リリースと延期範囲

初期リリースでは、Provenanceの最小基盤に加えてIdentity・Spatialの不変値と明示的投影を
実装する。次にTemporal、Schemaを既存検索・解決経路へ接続し、Rightsは情報保持と確認状態
までを実装する。

次は初期リリースへ含めない。

- fuzzy matchingや自然言語による地域・時間の推定
- CRSデータベースやgeometry変換の同梱
- schema間の自動migrationや暗黙の形式変換
- ライセンス互換性・法的可否の自動判定
- 完全な監査ログ、改ざん防止署名、実行環境SBOM

延期は機能価値を否定するものではない。各機能の前提データ、更新責任、誤判定時の救済手段を
先に確立するための境界である。

## 7. 最終判定

候補はすべて「ドキュメントとして採用」、実装は上記ゲートを通過したものだけを段階的に
採用とする。これにより、Rhinestoneの中心原則である「データを処理する前に、何を扱って
いるかをSpecとして確定する」を、共有知識の拡張にも適用できる。
